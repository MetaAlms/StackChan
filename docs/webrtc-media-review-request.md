## 3. 未接受的评审建议（请确认是否成立）

评审 Q2 推荐最小路径：

```
上行：24k 采集 → 重采样/AFE 16k → Opus 16k 编码 → RTP(48k 时钟)
下行：raw Opus → 解码 24k → 24k 播放
```

**本版未采用**，因为**用户最新明确要求"媒体链路 + 48kHz 重采样"**。
本版按用户要求设计为上行 16→48 后 48k 编码、下行 48k 解码后 48→24，
并在 SPEC §2.2 明确标注这是**用户指定的实现选择**，同时写明两项代价：

1. **升采样不能恢复 AFE 已丢失的高频**（AFE 奈奎斯特 8 kHz）
2. 相比最小路径**多两次重采样**，增加 CPU 与延迟

并在 SPEC §8 Q1 / PLAN R2 保留回退决策点：**若 M2-5 实测 CPU 超预算，
是否允许回退 16k 编码。**

**请确认：** 该处置是否满足"说明这是用户指定的 PCM 实现选择"的要求，
以及回退决策点位置是否合适。

## 4. 请重点复核的问题

### Q1 M1.5 的三类判定是否可执行？

SPEC §6.2 定义"目标通过 / 目标失败 / 实验无效"，并给出 T1–T4。
**"实验无效"的三个触发条件（T1 失败、媒体时间轴错误、播放时上行中断）
是否足以覆盖主要假阴性来源？还有哪些应判为实验无效的情形？**

### Q2 "不产生自身声音导致的新轮次"如何量化？（SPEC §8 Q4）

T2 的通过条件依赖这一判定，但本版**未给出量化口径**。
按什么窗口、什么事件序列判定"新轮次来自自身声音"而非环境噪声？
是否应由 T1 正对照给出**基线误触发率**再作比较？

### Q3 实验有效性断言应内建吗？（SPEC §8 Q3）

T2 要求"播放期间发送计数持续增加"。本版建议内建**断言式检查**
（采样周期内计数未按预期增长即判实验无效并中止），
而不是事后人工比对日志。**这个做法是否合适？阈值如何定？**

### Q4 跨通道边界如何构造可验证的乱序场景？（SPEC §8 Q2）

控制事件有 `response_id`，RTP 未必有对应关联。本版在 SPEC §4.5 第 4 条
要求"最小回路须专门验证乱序场景"，PLAN 2.5 列为任务，
但**未给出构造方法**。是否需要在桥接层引入独立的**媒体序号 → 播放代际**映射？
该映射如何验证？

### Q5 M4 边界是否还需收紧？

本版已按评审保留 Ogg/背压/门控。**是否还有其他被 WebSocket 或公共功能共用、
不应在 M4 触碰的组件？** 特别希望确认：本地 VAD 是否确实只用于 UI/检测，
停止驱动 WebRTC 轮次后是否可保留。

### Q6 是否仍存在"走完才发现不可行"的路径？

本版的止损点：P0 契约冻结 → M1 四层可观测 → **M1.5 AEC 三类判定** → M2-5 CPU 实测。
**这些是否足够靠前？** 还有哪些风险应在更早阶段验证？
