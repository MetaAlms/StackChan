## 0. 本版相对基线的修订

| 评审问题 | 优先级 | 本版处置 |
|---|---|---|
| 把"WebRTC 内置 AEC"当作已证实的服务端能力 | P1 | §1.3 降级为**待验证假设**；验收改为可观测行为，不引用抑制量 |
| 把 Opus 的 48k RTP 时钟当成 PCM 必须 48k | P1 | §2.2 订正为两个独立维度；48k PCM 标注为**用户指定的实现选择** |
| M1.5 用"任意本地 TTS + 空转写"判定 AEC | P1 | §6.2 改为**同一会话真实下行播放 + 近端正对照 + 远端独说 + 双讲 + 插话后再说话**；结果分**目标通过/目标失败/实验无效** |
| 假定全双工可直接复用会话逻辑 | P1 | §4.5 / §4.6 加入连续采集、本地停止旧播放、在途任务隔离、跨通道边界、重连清理 |
| M4 删除回退所需依赖 | P1 | §5.3 收紧为**只清 WebRTC 路径**；Ogg 提示音等公共依赖保留 |
| 回调内存、包时长、资源验收不足 | P2 | §4.3 / §4.4 / §6.5 补齐借用语义、有界非阻塞队列、120 ms 包、峰值 heap/栈/重连 |

### 未被本版接受的评审建议

评审 Q2 推荐"上行 16k 编码、下行直接解码 24k"的最小路径。
**用户最新明确要求 48 kHz PCM 编解码与显式重采样**，本版按用户要求设计，
并在 §2.2 与 §4.6 说明该选择的性质与代价，在 §8 Q1 保留回退讨论。

评审指出的其余事实与缺陷（F1/F3/F4/F5/F6/F7 的边界、A9、B16–B18）**全部采纳**。

## 1. 背景与目标

### 1.1 迁移动机

阿里云 WebSocket 协议**官方规格明确不做回声消除**（"无，需客户端自行处理"），
实测导致设备听到自身喇叭并自我打断；设备侧补 AEC 又因 `esp_codec_dev`
最多 2 通道而拿不到第 3 路回采参考（见 [aec-limitation.md](aec-limitation.md)）。

WebRTC 协议的官方选型表把回声消除/降噪标为"内置"，弱网对抗标为"良好"。
迁移的**预期**是获得可用的打断能力，并免除为对抗服务端突发推送而写的背压逻辑。

### 1.2 已达成的前置条件

M0 在真机验证（esp_peer **1.5.5**）：

| 环节 | 状态 | 边界 |
|---|---|---|
| SDP 交换（HTTP POST offer → answer）| ✅ 已通 | — |
| ICE | ✅ `Connection OK` | — |
| DTLS 与相关密钥建立 | ✅ 已通 | **不等于** SRTP 媒体收发已验证 |
| SCTP / DataChannel | ✅ `DATA_CHANNEL_OPENED` | — |
| `session.created` / `session.updated` | ✅ 收到 | 本次在服务端 `txt` 通道 stream 1 |

**重要限定**：`CONNECTED` 与 DataChannel 事件**不能证明未执行的媒体路径已可用**。
实际 RTP/SRTP 收发、解码播放与持续负载全部由 M1/M1.5 的媒体探针验证，
本 SPEC 不预称其可用。

### 1.3 迁移收益是待验证假设（P1）

**服务端是否对裸 esp_peer/RTP 提供可用的回声控制，目前证据不足，本 SPEC 按假设处理。**

评审依据：

- [RFC 7874 §5](https://www.rfc-editor.org/rfc/rfc7874.html#section-5) 建议**端点设备**实现 AEC；
  补偿无 AEC 的远端属可选项
- [W3C echoCancellation](https://www.w3.org/TR/mediacapture-streams/#dom-mediatrackconstraintset-echocancellation)
  是**采集侧**约束
- 阿里 [WebRTC 接入](https://help.aliyun.com/zh/model-studio/realtime-webrtc-access)
  示例使用浏览器 `getUserMedia`（自带采集侧 3A）；
  [AOQ 自定义采集](https://help.aliyun.com/zh/model-studio/aoq-custom-audio-capture)
  把 3A 配置放在**客户端 SDK**

因此协议选型表里的"内置"**不能推出**裸 RTP 会自动获得服务端回声处理；
但这些证据也**不能反证**服务端没有远端回声处理。

**验收必须写成可观测行为，而不是抑制量：**

> 播放期间持续上行，设备**既不因自身声音产生新轮次/取消**，
> 又能**识别近端人声插话并停止旧回答**。

服务端 VAD 与 AEC 是**不同能力**：`speech_started` 只表示检测到语音活动，
**不是 AEC 状态或抑制量指示器**。服务端事件未提供 AEC 后 PCM 的观测接口，
因此**不得从"空转写"反推 ERLE 或给出 dB 抑制量**。

### 1.4 非目标

- 视频（`video_dir` 保持 `NONE`）
- 移除 WebSocket 实现（见 §5.3，回退能力是硬需求）
- 修复 esp_peer 1.5.6 的 ICE 缺陷（属上游，见 [firmware-findings.md](firmware-findings.md) A8）

## 2. 关键事实与约束

### 2.1 事实核验结果（含评审订正）

| # | 主张 | 判定 | 本版采用 |
|---|---|---|---|
| F1 | esp_peer 不做 Opus 编解码 | ✅ 成立于当前默认实现 | 应用负责编解码；`nm` 无符号仅为辅助证据，不能单独证明所有处理能力 |
| F2 | WebRTC Opus 固定 48k，故 PCM 必须 48k | ❌ **不成立** | **RTP clock 固定 48k；PCM rate 独立可配**（§2.2）|
| F3 | esp-sr AFE 固定 16k | ✅ 当前管线成立 | 不扩大为所有 AFE 实现的普遍限制 |
| F4 | 板级采集/播放 24k | ✅ 当前配置成立 | 12k 是奈奎斯特上限，**非实测有效带宽** |
| F5 | 已有 48k 编解码能力 | ✅ 成立 | 但**无需据此新增 48k 链**；本版按用户要求使用 48k（§2.2）|
| F6 | 事件在 `txt`、stream 1 | ✅ 本次观测成立 | **不硬编码为 1**，每次会话经 channel 回调发现（§5.1）|
| F7 | SRAM 37k / 最低 24k | ✅ 历史读数成立 | **媒体预算未证**；M0 绕过正常音频初始化，不能作并行运行的资源基线（§6.5）|

### 2.2 采样率：两个独立维度（P1）

```
RTP/SDP 时钟  = 48000 Hz   ← RFC 7587 §4.1/7 固定，不可改
PCM 采样率    = 可独立配置  ← 编码输入 / 解码输出各自独立
```

`opus/48000/2` 中的 `/2` 也**不要求**每个 payload 都是双声道。

**本版采用 48 kHz PCM（用户明确指定）。这是实现选择，不是规范要求：**

| 路径 | 内容 |
|---|---|
| 上行 | 24k 采集 → 现有 24→16 + AFE 16k → **独立 16→48 单声道重采样** → **48k PCM Opus 编码** → RTP（48k 时钟）|
| 下行 | raw Opus packet → **48k 单声道解码** → **48→24 重采样** → 板级 24k 播放 |

**必须随设计一并说明的代价：**

1. **16k→48k 升采样不能恢复 AFE 已丢失的高频。** AFE 输出奈奎斯特上限 8 kHz，
   升采样只改变采样率，不产生新信息。上行有效带宽仍受 AFE 限制。
2. 相比"16k 编码 + 24k 解码"的最小路径，本选择**多两次重采样**
   （升采样 + 降采样），增加 CPU 与延迟；换来的是与板级 24k 链路、
   以及后续可能绕过 AFE 的直采路径在采样率上对齐。
3. **`esp_peer` 的 `audio_info.sample_rate` 保持 48000**，与 PCM 配置无关。

评审核验的 API 依据：`esp_opus_enc.h:70` 允许 8/12/16/24/48k；
`esp_opus_dec_open` 把 sample_rate 直接传给 `opus_decoder_create`，支持 24k 与 48k 输出。

**是否改回 16k 编码，见 §8 Q1。**

### 2.3 时间轴与 pts（P2）

**`esp_peer_audio_frame_t.pts` 单位为毫秒。** 评审已从实际 1.5.5 二进制确认
（库 SHA-256 `25a338fc6b05f702947c2af0e924f2dd3006503908e889dcdc512782d0ea3a58`，
对应 `peer_default.c:1471`、`rtp.c:403/416`）：

```c
// 二进制等价逻辑，非官方公开源码
peer_send_audio(frame) { rtp_encoder_encode(enc, frame->pts, frame->data, frame->size); }
rtp_timestamp          = (uint32_t)(pts_ms * 48);                        // Opus 分支
frame_pts_ms           = (uint64_t)raw_rtp_timestamp * 1000 / rate;      // 接收侧
```

| 包时长 | 48k PCM 样本/声道 | pts 增量 | RTP timestamp 增量 |
|---|---:|---:|---:|
| 20 ms | 960 | 20 | 960 |
| 60 ms | 2880 | 60 | 2880 |

**时间轴规则：**

1. **按采集/媒体时间累计，不按"已成功发送包数"。** 缺帧、主动丢弃、DTX
   都必须**推进时间轴**，否则服务端看到的时间与真实音频不符。
2. **发送必须实时 pacing**，不得把预录音频一次性倾倒。
3. **媒体时间轴独立于旧的 `timestamp_queue_`**（那是为小志服务端 AEC 对齐设计，
   本方案不使用）。
4. **接收侧 pts 不可直接当本地播放截止时间**：未扣首包原点、未扩展 32 位回绕。
   48k 完整回绕周期约 24 小时 51 分，随机起点可使首次回绕更早。
   桥接层须定义**新会话/SSRC 的重置、相对时间基准与回绕处理**。
5. **正确的时间轴只保障媒体调度，不证明服务端 AEC 已有参考或正确对齐**（§1.3）。

### 2.4 包边界与容量（P2，关联 A9）

**esp_peer 的 Opus RTP 发送路径未见 payload 长度校验。**
评审证据（同上库 SHA）：DWARF `rtp_encoder_t.buf` 长度 **1428**；
Opus 走 `rtp_encoder_encode_generic`（原源 `rtp.c:315`），函数偏移 `0x77–0x85`
**直接 memcpy 完整 size 到 `buf + 12 + ext_reserve`，此前无大小检查或分片**。
`peer_send_audio` 把应用的 `frame.data/size` 直接交给 RTP encoder。

**因此：**

- 应用必须**自行限制单个 raw Opus packet 的长度**
- **1428 字节是整个包缓冲，不是 payload 容量**；须扣除 RTP 头与可能的扩展预留
- **不得**传入大块 PCM、Ogg 封装、多包拼接或带自定义长度前缀的 payload
- 上限按实现容量与路径 MTU 取小者，桥接层显式校验、超限丢弃并计数

### 2.5 帧时长与解码器复用（P2）

- 合法 Opus packet 时长**可达 120 ms**；不得假定远端固定 20 ms。
  发送侧设定时长（§4.6）**不代表接收侧也如此**。
- **同一流内 ptime 变化不得重建 decoder**，否则丢失编解码状态。
  应按实际解码样本数分配 PCM 缓冲。
- SDK decoder 默认 INVALID 配置仅按 60 ms 计算建议空间，对 120 ms 包不足，
  需按最大合法时长预留。
- `useinbandfec` 写在 SDP 里**不会自动恢复丢包**，须验证实际恢复路径。

### 2.6 可重建性约束（P2）

`xiaozhi-esp32/` 与 `managed_components/` **均未被主仓库跟踪**
（`fetch_repos.py` 的产物）。因此：

- **任何实现改动必须落在可重建的 patch 或桥接代码中**
  （`firmware/patches/` 与 `firmware/main/` 下），不得只改未跟踪目录
- `python3 fetch_repos.py` 必须能从零重建出等效工程
- 每个里程碑结束前验证：删除 `xiaozhi-esp32/` 与 `managed_components/` 后重建，
  改动仍存在

## 4. 架构

### 4.1 数据流

```
【上行】
ES7210 24k 2ch
 └─ 现有重采样 24k→16k + AFE（16k 单声道）
     └─ 独立重采样 16k→48k 单声道        ← 本版（§4.6 契约）
         └─ Opus 编码 48k 单声道          ← 本版
             └─ esp_peer_send_audio()（pts = 媒体毫秒，§2.3）→ RTP/SRTP

【下行】
RTP/SRTP → on_audio_data（raw Opus packet，借用内存）
 └─ 回调内复制 payload 与元数据 → 有界非阻塞队列      ← §4.4
     └─ worker：按实际包时长解码 48k 单声道            ← §2.5
         └─ 重采样 48k→24k
             └─ 板级播放（受 §4.5 本地停止与代际检查控制）

【控制面】
DataChannel（会话发现 stream）⇄ JSON 事件
```

### 4.2 时间轴

见 §2.3。要点：pts 毫秒、按媒体时间推进、实时 pacing、接收侧需重置与回绕处理。

### 4.3 包边界

见 §2.4。要点：单包 raw Opus、1428 是整包缓冲、显式容量与 MTU 校验。

### 4.4 回调内存与队列（P2）

评审确认：实际 `on_audio` 在**栈上**构造 frame，payload 指向 RTP/jitter 接收内存，
**回调返回后即被释放/复用**。

**硬约束：**

1. **异步消费必须在回调返回前复制 payload 与所需元数据。**
2. **回调内不得阻塞。** 默认实现由 peer 主循环驱动收包/状态；
   在回调里做解码、播放或 `wait=true` 等队列，
   会**同时阻塞 ICE、RTCP、SCTP 与取消事件**。
3. **UDP 没有 TCP 那样的服务端背压**——现有 WebSocket 的背压思路不可移植，
   满队列必须有明确定义的丢弃/恢复策略。
4. 队列容量**按时间与字节双预算**设计，不直接沿用 WebSocket 的 8 秒缓存（§4.7）。

### 4.5 全双工与本地打断（P1）

**评审确认的现状障碍：**

| 位置 | 问题 |
|---|---|
| `application.cc:979` | 说话时关闭非 Realtime 模式的采集；现有 Aliyun `SendAudio` 也有上行门控 |
| `audio_service.cc:613` | `EnableVoiceProcessing` 每次 enable 都重置 decoder/输入重采样并进入 warmup |
| `application.cc:1007–1012` | `AbortSpeaking` 仅写 `aborted_` 并发送 cancel；**`aborted_` 没有读取方**，不停止本地队列 |
| `audio_service.cc:702–713` | `ResetDecoder` 清队列，但解码任务在锁外处理后**重新入队**；播放任务出队后即写设备。**清队列不撤销处理中任务** |

**设计要求：**

1. **会话期间连续采集。** 不得频繁开关 `EnableVoiceProcessing` 制造"空转写"。
2. **接收媒体不以异步 UI `speaking` 状态为唯一门控**——
   RTP 可能先于控制事件到达，会丢首帧。§4.6 给出替代门控。
3. **本地停止旧播放**需要可实现的任务，不能依赖服务端 cancel：
   - 定义**会话/响应代际**（generation）
   - **丢弃过期解码结果**，隔离在途解码与输出任务
   - 当前输出需有**停止路径与有界尾音**
4. **跨通道边界必须专门处理**：控制事件带 `response_id`，
   而 **RTP payload 未必有对应关联**，不能假定"加一个 generation
   就能自动关联 `response_id` 与 RTP"。最小回路须专门验证乱序场景。
5. **打断不得清掉用户正插话的上行**；仅换会话/断线才清理旧上行与未完成任务。
6. 服务端取消按本模型支持处理，**不照搬其他厂商的 truncate/output-buffer 语义**。

### 4.6 48k 转换契约（P2）

**重采样（`esp_ae_rate_cvt`）：**

- `sample_num` 为**每声道**样本数
- 先查容量（`esp_ae_rate_cvt_get_max_out_sample_num`），
  再调 process 并**检查返回值**
- **只使用 `actual_out`**，不得假定输出长度等于理论值
- **保留跨帧余量与滤波状态**（同一转换器实例跨帧复用，不逐帧重建）

**Opus 编码（48k 单声道）：**

- 编码器配置 `sample_rate` = 48000、`channel` = 1
- 用 `esp_opus_enc_get_frame_size` 取得帧样本数，**与重采样输出对齐**
- **初始关闭 DTX**（DTX 会使时间轴出现跳跃，干扰 §2.3 的规则）
- 每个 packet 的元数据（样本数、时长）与实际内容一致

**帧时长选择：**

- 20 ms 与 60 ms 的选择**仅作用于 WebRTC 路径**
- **不得全局修改 `OPUS_FRAME_DURATION_MS`**，否则破坏 WebSocket 与 AFE
  （现有 `MAX_DECODE_PACKETS_IN_QUEUE` 等常量依赖它）
- 需要不同帧长时，通过**独立的 WebRTC 编码实例**实现

**失败处理：**

- **重采样或编码失败时不得把 48k PCM 按 24k 播放**（或反之）——
  采样率错配会产生变速失真且难以从日志发现，必须显式报错并计数

### 4.7 队列预算（P2）

评审给出的现有时长（供对比，**不得直接沿用**）：

| 现有 AudioService 队列 | 帧数 | 每包 60ms | 每包 20ms |
|---|---:|---:|---:|
| decode | 133 | 7.98 s | 2.66 s |
| send | 40 | 2.4 s | 0.8 s |
| encode / playback（各自）| 2 | 120 ms | 40 ms |

另有处理中任务与 I2S 缓冲，**`playback=2` 不能单独证明足够**。

**设计要求：**

- 队列容量**按时长、字节与目标延迟**三者设计，不由帧数直接换算
- 明确 **jitter 缓冲**（esp_peer 已有）与 **PCM 播放缓冲**（应用侧）的职责划分，
  **不重复堆叠两个长抖动缓冲**
- esp_peer 本机 M0 已设 100 ms / 32 KiB jitter、32 KiB send pool
  （**非默认值**）；默认值为 100 ms timeout / 100 kB
- 需测**总排队时长、欠载/溢出、迟到率**

## 5. 接口

### 5.1 esp_peer 用法（与 M0 的差异）

| 项 | M0 | 本 SPEC |
|---|---|---|
| `audio_dir` | `SEND_RECV`（未发数据）| `SEND_RECV`（实际收发）|
| `audio_info.sample_rate` | 48000 | **48000（不变）** |
| `esp_peer_send_audio()` | 未调用 | 按 §2.3 实时 pacing 调用 |
| `on_audio_data` | 仅计数 | 复制后入队，不阻塞（§4.4）|
| 通道与 stream | 记录并用于回复 | **每次会话经 channel 回调发现，不硬编码 stream 1** |

### 5.2 与 xiaozhi 音频服务的边界

**复用**：采集/播放任务、`ReadAudioData`（含 24→16）、AFE 实例、
编解码任务的线程与队列模型。

**新增**：16↔48 重采样、48k Opus 编解码实例、
`esp_peer` 与队列之间的桥接（含复制、代际、容量校验）。

**需要改造**（§4.5）：连续采集、本地停止、在途任务隔离、跨通道边界。

### 5.3 协议层边界与回退（P1）

**复用**：emoji 表情解析、会话配置构造、错误处理。

**替换**：传输由 WebSocket 文本帧改为 DataChannel；
音频由 `input_audio_buffer.append`（Ogg）改为 RTP。

**M4 只清理 WebRTC 路径，不得删除回退依赖。** 评审确认：

> `AudioService::PlaySound`（`audio_service.cc:667`）仍使用 `OggDemuxer`
> 播放**本地提示音**，它不是 WebSocket 专属。

保留清单：Ogg muxer/demuxer、背压逻辑、轮次/半双工逻辑，
以及所有 WebSocket 回退所需路径。WebRTC 路径**绕开**它们，
必要时按协议分支**收紧作用域**而非删除。

**不得一边要求随时回退（F8），一边删除其功能依赖。**
真正删除回退实现必须先修改 F8 并另行评审。

## 6. 验收标准

### 6.1 M1：上行通路（预录 raw Opus）

**配置与 fixture 要求：**

1. **等 `session.updated`** 后再发媒体
2. **明确启用**当前模型支持的 `input_audio_transcription` 并**检查配置回显**；
   不把 SDK 参数直接写成 JSON 字段名
3. **一次编码并发送一个完整 raw Opus packet**，保持实际节奏；
   **不传 Ogg、PCM、多包拼接或带长度前缀的 payload**
4. fixture **含前后静音**，尾部至少覆盖配置的 `silence_duration_ms` 并留余量——
   避免发完语音就停发，导致 VAD 观察不到静音
5. 固定模型、fixture hash、PCM 参数、Opus 参数与预期关键词
6. **先用 20 ms 包建立基线**，再测 60 ms 评估复用成本。
   注意 `minptime=20` **不证明远端固定 20 ms**（§2.5）

**必须记录**（区分失败层级）：

| 类别 | 记录项 |
|---|---|
| 配置 | `session.updated` 回显、转录配置 |
| 发送 | `esp_peer_send_audio` 返回值、包数/字节/**媒体时长** |
| VAD | `speech_started` / `speech_stopped` |
| ASR | 转写内容、`transcription.failed`、超时 |

**退出条件：**

| 编号 | 判据 |
|---|---|
| M1-1 | 出现 `input_audio_buffer.speech_started` |
| M1-2 | 转写关键内容与 fixture 一致 |
| M1-3 | **5 分钟资源检查** |

**"无转写即证明传输失败"是过强的结论**——须按上表区分是配置、发送、VAD 还是 ASR 失败。

### 6.2 M1.5：AEC 假设验证（P1，核心）

**不再使用"任意本地 TTS + 空转写"的二元判据。**
改用**同一会话的真实下行播放**作远端刺激，并做近端正对照。

M1.5 提前接入麦克风与服务端实际音频解码播放，**只做媒体、事件与测量**，
暂不接完整 UI/表情。记录**实际播放 PCM 及时间**——
**不把"服务端生成完成"视为"设备播放完成"**。

**测试矩阵：**

| # | 测试 | 必要控制 | 通过条件 |
|---|---|---|---|
| T1 | **喇叭关闭 + 近端人声**（正对照）| 确认 ASR 配置；采集/编码/发送正常 | 三个不同短句识别关键内容 |
| T2 | **仅真实远端播放** | 正常与最高预期音量；**播放期间发送计数持续增加**、麦克风确实存在声学回声 | 多次连续 ≥30 s 播放，**不产生自身声音导致的新轮次/取消** |
| T3 | **远端播放 + 人声插话** | 近端短句与远端内容不同；音量/距离/阈值保持一致 | 新问题可识别、**旧播放实际停止**并改答新问题 |
| T4 | **插话之后再次说话** | 检查取消后的采集与会话状态 | 继续正常识别与回应 |

**必须先排除的混淆**：本项目**已存在"播放时关闭采集/丢上行"的逻辑**，
会直接污染 T2 的判据，必须确认该逻辑在 M1.5 中不生效（§4.5 连续采集要求）。

**结果判定为三类，不是二元：**

| 判定 | 条件 | 动作 |
|---|---|---|
| **目标通过** | T1–T4 全通过 | 允许继续投入 M2 |
| **目标失败** | **实验有效**前提下 T2 或 T3 不达标 | **交 Codex 评审后决策**；不得用半双工门控掩盖 |
| **实验无效** | T1 失败、媒体时间轴错误、或**播放时上行中断** | **先修实验**，不得据此判定 AEC |

**明确禁止：**

- **没有 AEC 后 PCM 观测或其他可靠仪器时，不得从"空转写"计算 ERLE 或给出 dB 抑制量**
- **不得把 `speech_started` 当作 AEC 指示器**
- **M1.5 通过只允许继续投入，不能取代 M3** 在更多音量、距离、噪声与重连条件下的验收

**可提议的产品目标（待测，非既有保证）：**
`speech_started → 旧音频停止` 的 p95 ≤ 200 ms；真实插话起点至停止另计。

### 6.3 M2：产品接入

接产品音频服务与事件/UI，包含 §4.5 的本地打断、在途任务隔离与状态机改造。

| 编号 | 判据 |
|---|---|
| M2-1 | 下行音频可听且清晰，无断流 |
| M2-2 | `server_vad` 正常结束轮次，无需本地 VAD |
| M2-3 | 接回表情联动 |
| M2-4 | 连续采集生效（播放期间上行不中断）|
| M2-5 | 48k 编码与重采样耗时实测（p95/p99）|

### 6.4 M3：打断、稳定性与量化

| 编号 | 判据 |
|---|---|
| M3-1 | **不自打断**：≥30 s 连续说话不产生自身新轮次 |
| M3-2 | **真实插话**：识别并停止旧回答，改答新问题 |
| M3-3 | 补抖动/丢包/长时/断网重连验证 |
| M3-4 | **量化停止延迟**（p50/p95），按 §6.2 目标口径 |
| M3-5 | 多音量/距离/噪声条件下复验 |

**M3-1 失败时不得通过"加回半双工门控"来掩盖**——那等于未获得迁移收益。
应定位是**采集门控、时间轴、排队、VAD、回声参考还是残余回声**，
不能一律归因 AEC。

### 6.5 资源验收（P2）

**不以 M0 读数或"内部 SRAM > 8 KiB"作为可行性判据。**
评审指出：M0 分支**绕过正常 `Application` 音频初始化**，
且 `free sram` **只测 `MALLOC_CAP_INTERNAL`**。

**必须实测：**

| 类别 | 项目 |
|---|---|
| heap 能力 | internal+8bit、DMA、PSRAM 各自的 free / minimum / **largest block**、分配失败 |
| 栈 | 各 task 的**高水位** |
| 耗时 | 双向 encode/decode/SRTP/AFE 的 p95/p99、deadline miss、主循环阻塞 |
| 音频 | 播放**欠载**次数与时长 |
| 场景 | 首次建连 / 重连 / 长响应 / 队列接近满 / 取消后回落 |
| 负载 | 双向 + AFE + UI **同时运行** |

**DTLS 与 SRTP 分开测**：DTLS 是**建连**开销（测握手峰值），
SRTP 是**持续媒体**开销（测稳态）。
**不得由双核或硬件加密支持推定实时预算足够。**

**10 轮是功能冒烟，不代表长时稳定**——需持续双向、抖动/丢包与重复重连。
**重建连接需重新发现事件 stream、重新完成 SDP/会话初始化，并隔离旧回调与数据。**

N2 的"局域网"改为明确 **Wi-Fi 条件 / 地域 / 网络条件下**的测量目标与分位数
（阿里端是云端）。

## 7. 约束与风险

### 7.1 约束

| 项 | 值 |
|---|---|
| ESP-IDF | v5.5.4 |
| esp_peer | **锁定 1.5.5**，不可升 1.5.6（ICE 缺陷，见 findings A8）|
| PSRAM | 8 MB |
| 内部 SRAM | 历史读数 37 KB / 最低 24 KB（**媒体预算未证**，§6.5）|
| 可重建性 | 改动须落在 patch/桥接代码（§2.6）|

### 7.2 风险

| 编号 | 风险 | 出现时机 | 应对 |
|---|---|---|---|
| **R1** | **服务端无可用回声控制** | **M1.5** | 按 §6.2 判"目标失败"→ Codex 评审决策；不掩盖 |
| R2 | 48k 编码 + 两次重采样 CPU 超预算 | M2-5 | 实测 p95/p99；必要时回退 16k 编码（§8 Q1）|
| R3 | 资源不足 | §6.5 | 按能力 heap 实测；大缓冲显式落 PSRAM 并验证 |
| R4 | 回调借用内存被滥用 | 实现期 | §4.4 复制要求 + 静态检查 |
| R5 | 包超长越界（A9）| 实现期 | §2.4 容量校验 + 超限丢弃计数 |
| R6 | 全双工改造牵动状态机 | M2 | §4.5 列出可实现任务；M1.5 先验证最小回路 |
| R7 | 上游不修 ICE 缺陷 | 长期 | 已接受，锁 1.5.5 |

### 7.3 回退

WebSocket 实现**完整保留**，Kconfig 切换。**M4 之前不做破坏性删除**（§5.3）。
M1.5 判"目标失败"时回退，保留全部既有功能（对话、识别、表情、背压），仅放弃打断。

## 8. 开放问题（请评审回答）

**Q1：48k PCM 是否应改回评审建议的 16k 编码 / 24k 解码？**
本版按用户明确要求采用 48k。但评审指出该最小路径已核验可行且更省资源。
**若 M2-5 实测显示 48k 路径的额外重采样使 CPU 超预算，是否允许回退 16k 编码？**
（本版倾向：允许，并应在 PLAN 中预置该回退点。）

**Q2：§4.5 第 4 点的跨通道边界如何设计可验证？**
控制事件有 `response_id`，RTP 未必有对应关联。最小回路应如何构造乱序场景？
是否需要在桥接层引入**独立的媒体序号 → 播放代际**映射？

**Q3：M1.5 的"实验无效"判定如何自动化？**
T2 要求"播放期间发送计数持续增加"——是否应内建**断言式检查**
（如采样周期内发送计数未按预期增长即判实验无效并中止），
而不是事后人工比对日志？

**Q4：T2 的"不产生自身声音导致的新轮次"如何量化？**
按什么窗口、什么事件序列判定"新轮次来自自身声音"而非环境噪声？
是否需要 T1 的正对照给出基线误触发率？

**Q5：M4 的边界是否还需收紧？**
本版已按评审保留 Ogg/背压/门控。是否还有其他**被 WebSocket 或公共功能共用**
的组件不应在 M4 触碰？
