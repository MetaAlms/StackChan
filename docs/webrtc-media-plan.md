# WebRTC 媒体链路 实现计划

对应 [webrtc-media-spec.md](webrtc-media-spec.md)。本文件只定义"怎么做、分几步、
每步的退出条件"，不含日期承诺。

状态：**待修改**（2026-10-08 评审未通过，见 [评审结果](webrtc-media-review-result.md)）。

---

## 原则

1. **每步都能独立止损。** 不把"发现不可行"推迟到最后一步。
2. **M1 尽量不碰现有音频服务。** 先用预录音频走通通路，把音频服务改造推迟到 M2。
3. **不删除任何现有实现**，只新增与切换。回退成本必须保持为零。
4. **每个里程碑结束都要有可复现的日志证据**，写进 `docs/`，不留在对话里。

---

## 里程碑总览

| 里程碑 | 目标 | 回答的问题 | 失败时 |
|---|---|---|---|
| **M1** | 上行 RTP 通路 | 编解码 + RTP + 服务端 VAD/ASR 能否工作 | 换实现或止损 |
| **M1.5** | **AEC 早期判据** | **服务端 AEC 是否可能有效** | **止损，回退 WebSocket** |
| **M2** | 双向 + 接麦克风 | 完整对话可用 | 回退 |
| **M3** | 打断与稳定性 | M2-3 / M2-4 达成 | 回退 |
| **M4** | 清理与收尾 | 删除 WebSocket 专用补丁 | — |

**M1.5 是新增的早期止损点**，对应 SPEC §8 Q2。它把"迁移是否值得"这个问题的
答案从 M3 提前到 M1 之后，代价很小。

## M1 — 上行 RTP 通路

### 目标

用**预录音频**（不接麦克风）经 48 kHz Opus + RTP 送至服务端，
确认服务端能识别。

### 为什么用预录音频

- 完全不碰 `AudioService`、AFE、编解码队列
- 失败时能确定是"传输/编解码"问题，而非音频服务改造问题
- 工作量约为接麦克风方案的 1/3

### 任务

| # | 任务 | 产出 |
|---|---|---|
| 1.1 | 初始化 48 kHz Opus 编码器（`esp_opus_enc_open`，复用 `esp_audio_codec`） | 能编码一帧并打印字节数 |
| 1.2 | 准备测试音频：16 kHz 单声道 PCM（可用 Mac 生成后嵌入或从 SD 卡读） | 一段 5–10 s 可辨识语音 |
| 1.3 | 16 kHz → 48 kHz 重采样（`esp_ae_rate_cvt`） | 重采样后长度正确 |
| 1.4 | 在 M0 基础上加入 `esp_peer_send_audio()` 调用（60 ms 一帧） | 帧按节奏发出 |
| 1.5 | 观察服务端事件 | 见下方退出条件 |

### 退出条件

| 编号 | 判据 | 来源 |
|---|---|---|
| M1-1 | 出现 `input_audio_buffer.speech_started` | DataChannel 日志 |
| M1-2 | `conversation.item.input_audio_transcription.completed` 的 `transcript` 与预录内容一致 | DataChannel 日志 |

**两条都达成 → 进入 M1.5。任一失败 → 记录日志，评估实现路线。**

### 需要先回答的问题

- `esp_peer_audio_frame_t.pts` 的语义与单位（SPEC Q4）——查头文件/示例/试错
- 阿里端是否接受非 48 k 的 Opus 协商（SPEC Q3）

## M1.5 — AEC 早期判据

### 目标

**在投入双向链路之前**，判断服务端 AEC 是否可能有效。

### 方法（待评审确认，见 SPEC Q2）

候选方案：

**方案 a（推荐）：设备播放 + 同时上行采集**
让设备播放一段可辨识音频（如 TTS 念一句话），同时把麦克风采集上行。
观察服务端转写结果：

- 转写内容 = 设备播放的内容 → **AEC 未生效**，设备听到了自己
- 转写为空或只有环境音 → **AEC 生效**

**方案 b：真机双向最简回路**
直接做 M2 的最小双向（不接表情、不接状态机），跑一次真实对话，
看设备说话时用户插话是否被打断。

### 退出条件

| 结果 | 动作 |
|---|---|
| 方案 a 显示 AEC 生效 | 进入 M2 |
| 方案 a 显示 AEC 未生效 | **止损**：保留 WebSocket，按 [aec-limitation.md](aec-limitation.md) 重评路径 |
| 方案 a 无法判定 | 落到方案 b，但仍限制在最小回路 |

**这一步的失败是"好消息"——它用很小代价避免了走完 M2/M3 才发现方向错误。**

## M2 — 双向链路

### 目标

接真实麦克风与喇叭，完成一次可用的双向对话（暂不要求打断）。

### 任务

| # | 任务 | 风险 |
|---|---|---|
| 2.1 | 上行接入 AFE 输出（16 k）→ 重采样 48 k → 编码 → 发送 | R4 |
| 2.2 | 下行：`on_audio_data` → 解码 48 k → 重采样 24 k → 播放 | Q3 |
| 2.3 | 48 kHz Opus 编码耗时实测 | **R2** |
| 2.4 | 会话配置改为 `server_vad`，**移除本地 VAD 驱动轮次** | — |
| 2.5 | 事件处理从 WebSocket 文本帧迁到 DataChannel（复用 emoji 解析与会话逻辑） | — |
| 2.6 | 表情联动接回（`SetEmotion`） | — |
| 2.7 | 内存峰值实测（内部 SRAM 最低余量 > 8 KB） | **R3** |

### 退出条件

M2-1、M2-2（SPEC §6.2）+ N2、N3、N4（SPEC §3.2）+ R-1、R-2（SPEC §6.3）

### 明确不做

- 不删除 WebSocket 实现
- 不删除 Ogg / 背压 / 排空守卫等补丁（留给 M4）

---

## M3 — 打断与稳定性

### 目标

达成 SPEC §6.2 的 M2-3（打断）与 M2-4（不自打断）。

### 任务

| # | 任务 | 说明 |
|---|---|---|
| 3.1 | 真机验证打断 | 设备说话时用户插话，设备应停止并改答 |
| 3.2 | 不自打断长时验证 | 设备连续说话 ≥ 30 s |
| 3.3 | 若 M2-4 失败：调整 `turn_detection` 参数 | `threshold` / `silence_duration_ms` |
| 3.4 | 若仍失败：评估服务端 AEC 的实际抑制量 | 可能需回报上游或改用他法 |
| 3.5 | 移除为 WebSocket 写的自打断守卫 | 服务端 AEC 生效后应不再需要 |

### 退出条件

M2-3 与 M2-4 **同时达成**。

**M2-4 失败时不得通过"重新加回半双工守卫"来掩盖**——那等于没获得迁移的收益。
此时应回退到 WebSocket，并如实记录。

---

## M4 — 清理与收尾

### 目标

删除仅为 WebSocket 能力缺失而存在的补丁，降低维护面。

### 待删清单（确认无回退需求后）

| 项 | 原用途 |
|---|---|
| `ogg_opus_muxer.{h,cc}` | 手工 Ogg 封装（WebRTC 用 RTP，无需容器）|
| Ogg demuxer 使用 | 下行解码 |
| 背压逻辑（`is_audio_payload` 内联 + `wait=true`）| 对抗服务端 3–5 倍速突发推送 |
| 排空守卫 / 延后提交 | 防止自身声音被误判为新轮次 |
| 本地 VAD 驱动轮次 | 服务端 WebSocket VAD 对 Ogg 不触发 |
| 半双工门控 | 无 AEC 时的自打断规避 |

**删除前必须确认 M3 已稳定运行一段时间**，且回退开关仍可用。

---

## 风险与应对

| 编号 | 风险 | 出现时机 | 应对 |
|---|---|---|---|
| **R1** | **服务端 AEC 无效** | **M1.5（已提前）** | 止损，回退 WebSocket |
| R2 | 48 k Opus 编码 CPU 超预算 | M2.3 | 降复杂度 / 降码率；实测后再决定 |
| R3 | 内部 SRAM 不足 | M2.7 | 大缓冲显式走 PSRAM；必要时裁剪其他功能 |
| R4 | 上采样伪影影响 ASR | M1-2 | M1 即可发现 |
| R5 | 上游不修 ICE 缺陷 | 长期 | 已接受，锁 1.5.5 |

---

## 回退

**任何阶段**都可回退：WebSocket 实现完整保留，Kconfig 开关切换。

回退后的状态 = 当前状态（对话、识别、表情、背压均可用，仅无打断）。

**M4 之前不做破坏性删除**，正是为了保证这一点。

---

## 需要评审确认的事项

1. **M1 用预录音频而非接麦克风**——是否认可这个缩小范围的做法？
2. **M1.5 的 AEC 判据设计**（SPEC Q2 / 本文方案 a）——方法是否成立？
   有没有更快或更可靠的判据？
3. **采样率链路是否接受"先保留 AFE、带宽限 8 kHz"**（SPEC Q1）？
   还是应在 M1 就验证绕过 AFE 的可行性？
4. **里程碑划分是否合理**？特别是 M1.5 的位置与代价。
5. **M4 的删除清单**是否有不该删的项？
6. **还有哪些没被识别出的风险**？
